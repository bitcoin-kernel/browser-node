bitcoin-kernel / browser-node — the demos

A Bitcoin testnet4 node, piece by piece, in a browser tab. The "live" demos use a WebRTC bridge to a real testnet4 peer (a tab can't open raw TCP); those links point at a running bridge. how it all works →

The node

Running node ▸ node.htmllive · needs bridge
The full pipeline in one dashboard: stream and validate the header chain, bootstrap the UTXO set from an assumeUTXO snapshot, validate blocks forward (full scripts and signatures, WASM secp, in a Web Worker), persist to OPFS, and check set-consistency with a SwiftSync 32-byte accumulator.
Toward a full node ▸ fullnode.htmllive · needs bridge
The same node split into two tabs — Node (sync, assumeUTXO, SwiftSync) which follows the live tip with a "listening" heartbeat, and Validation (the full-consensus block checks, in their own lane).
Follow the tip ▸ tip.htmllive · needs bridge
Syncs the header chain to the tip, then keeps pace — validating each new header (proof-of-work, BIP94 difficulty, linkage) as testnet4 mines it, reorg-aware, live in the tab.

assumeUTXO & SwiftSync

Verify the snapshot ▸ verify.htmlself-contained
Streams a Bitcoin Core dumptxoutset snapshot (the full 14.1M-coin UTXO set) through the SwiftSync accumulator and confirms it hashes to the commitment af37b01d… — holding only 32 bytes of state.
Validate from genesis ▸ fullchain.htmlneeds a local block-server
Streams blocks genesis→N through the SwiftSync accumulator (set-consistency) in the tab — the path past the 25 GB UTXO-set wall.

Propagation (the mesh)

Block propagation ▸ mesh.htmlopen in two tabs
Two browser tabs become Bitcoin peers to each other over WebRTC — no server in the data path. One pulls thousands of real blocks from the network and propagates them to the other, which validates every one. Set the count with ?blocks=N. Open this link in two tabs, connect both, then hit Seed.
